本文详细说明 MeshROC 的路由实现。阅读前建议先了解[技术总览](/docs/overview)。

## 受控洪泛基线

MeshROC 继承了 Meshtastic 的受控洪泛作为兼容基线。其核心规则如下：

1. 每个数据包携带一个由发送方生成的 `packet_id` 与源节点 ID。
2. 节点收到数据包后，先查询本地**去重表**（recent packet cache）。若该 `(源节点, packet_id)` 组合已存在，则直接丢弃。
3. 若为新包，则递减 `hop_limit`。当 `hop_limit` 归零时不再转发。
4. 转发前引入一段随机退避延迟，避免多个邻居节点同时抢占信道。

去重表是有限长度的环形缓冲。在节点密集、流量较大的网络中，去重表可能提前溢出，导致同一数据包被重复转发——这是洪泛机制在大规模网络中退化的典型表现。

## 洪泛的容量瓶颈

设网络中有 N 个参与转发的节点，一条消息在理想情况下会产生约 N 次空口发射。由于 LoRa 的空中时间较长（在 SF10/125kHz 下，一条短文本的空中时间可达数百毫秒），信道很快饱和。

实测经验表明，在使用默认参数的洪泛网络中，当参与转发的节点超过约 20–30 个时，消息投递成功率会明显下降。

## 分层骨干路由

MeshROC 通过**限制转发者集合**来解决上述瓶颈。

### 角色配置

每个节点通过配置项声明自己的角色：

```ini
# 骨干节点：参与转发
role = BACKBONE

# 终端节点：默认静默，不转发他人消息
role = CLIENT_MUTE
```

终端节点仍然可以正常收发自己的消息，只是不再充当中继。这样，参与转发的节点数从 N 降至骨干节点数 M（通常 M 远小于 N），信道压力随之大幅下降。

### 骨干节点选址原则

分层骨干的效果高度依赖骨干节点的选址。推荐原则：

- 优先选择山顶、楼顶等**视野开阔的制高点**；
- 相邻骨干之间尽量保持准视距（LOS）或轻度遮挡；
- 避免在同一片区域堆叠过多骨干节点，否则退化回洪泛；
- 骨干节点应具备稳定供电（太阳能或 POE）与可靠的天线安装。

## 自适应跳数

固定的 `hop_limit` 在实际部署中很难取到合适值：设得太小，边缘节点收不到消息；设得太大，小网络里会产生大量无意义的转发。

MeshROC 让骨干节点根据观测到的网络直径动态调整跳数上限：

- 节点持续统计收到的数据包中 `hop_start - hop_limit` 的分布，估计当前网络的实际跳数需求；
- 在此基础上留出一定裕量，作为本节点发出数据包的初始 `hop_limit`。

## 信噪比择优路径

在洪泛机制下，「谁先转发」基本由随机退避决定，与链路质量无关。这意味着一条消息可能经由一串信号勉强可用的弱链路传播，成功率很低。

MeshROC 将**退避时长与链路质量挂钩**：

- 收到数据包时记录其 SNR（信噪比）；
- SNR 越高的节点，退避时间越短，因而更可能抢先转发；
- 其他节点侦听到该转发后，通过去重机制抑制自己的转发。

其净效果是：消息倾向于沿着链路质量最好的路径传播，同时无需维护任何显式路由表，保持了洪泛的无状态优势。

:::note

以上机制均为**转发策略层面**的优化，不修改协议帧结构，因此不影响与标准 Meshtastic 设备的互通性。混合组网时，标准设备按原有洪泛规则工作，MeshROC 设备按优化策略工作，两者可以共存。

:::
